# IC研发工作台集成实践

芯智工作台 · v1.0.0 · 2026年9月6日

关键词：模拟IC研发、本地知识管理、内网AI、项目进度、数据安全

## 1 实践介绍

### 1.1 业务场景与问题

模拟 IC 研发人员需要同时处理项目文件、器件 Datasheet、评审笔记、阶段进度、待办和邮件。资料分散在目录和不同软件中时，查找原始依据、整理进度以及将阅读结果沉淀为笔记，需要重复切换和手动复制。

本项目将上述个人工作流程收拢到本地桌面客户端。文件与运行数据保存在本机；AI 使用用户配置的本地或内网模型。产品不调用具体 EDA 软件，不替代仿真、签核或工程师判断。

### 1.2 方案前后对比

| 工作环节 | 原有方式与困难 | 当前实现 |
| --- | --- | --- |
| 项目资料查阅 | 依赖目录和人工记忆定位，摘要与原文容易分离 | 只读授权目录、增量索引、关键词检索及带来源的 AI 候选分析 |
| Datasheet 阅读 | 原件阅读、参数摘录和摘要排版分开操作 | 原件分页阅读、按页文本与 AI 概略，保留单位、条件、来源 |
| 进度与日程 | 周报、风险和待办分散，历史变化不易追溯 | 项目目录绑定、星标、备注、历史快照和关联日历任务 |
| 知识沉淀 | 文本、图片和表格分散保存，导出方式不统一 | 三栏笔记、图文表格编辑、本地映射及四种导出格式 |
| 模型与邮件 | 工程内容发送范围和密钥保存方式不统一 | 默认离线、显式网络开关、系统凭据库及发送二次确认 |

以上对比来自本项目需求及实现，不是对任何团队既有系统的统计评价。

### 1.3 工作流程对比

原流程：寻找项目文件 → 用阅读器查看资料 → 复制参数到笔记 → 单独维护任务 → 汇总评审说明。

当前流程：授权项目目录 → 在工作台检索并核对原文 → 显式选择内容交给内网 AI → 人工确认后保存笔记 → 将重点任务关联项目与日历。AI 建议不会自动修改项目文件、进度或待办。

### 1.4 实际效果与适用边界

本地客户端已形成统一入口，包含工作台、智能对话、项目管理、Datasheet、知识笔记、Skills、格式转换、邮件、日历、计算器和软件启动器。普通版以干净数据开始；独立 Demo 使用合成项目、资料、邮件和确定性模型展示流程。

本轮复核补齐了 PDF 阅读的独立渲染、笔记 Word 结构化导出、PDF 图片嵌入、切换笔记时的未保存保护和既有笔记映射。测试结果与最终交付状态以仓库 COMPLETION_REPORT.md 为准。

复杂 PDF 表格、扫描件、公式和 AI 摘要仍须人工复核。DOC 为 Word 兼容 HTML，并非旧版二进制 DOC。邮箱采用受控同步、阅读与基础收发，不是完整邮件服务器或团队协同系统。应用内提醒需要客户端保持运行。

### 1.5 量化实践价值

当前可核实的工程数据为：11 个主导航工作入口、2 套独立应用、4 种笔记导出格式、36 项前端测试、30 项 Rust 测试和 4 项模拟模型协议测试。测试数量表明已有回归基线，不等同于全部输入或生产环境的覆盖率。

尚未开展真实业务计时、规模化试用或财务测算，因此不报告节约人天、成本金额或效率百分比。下一轮建议用同一组脱敏任务记录“资料定位耗时、摘要人工修正次数、任务维护耗时、导出失败次数”，比较中位数与失败率；在试用双方确认统计口径后再计算收益。

### 1.6 搭建心得

需求先进入管理文件，再建立对应验收项。重复要求按数据模型合并，例如项目历史与备注共用项目标识，日历只引用项目，不另建相互矛盾的项目副本。

复用成熟项目的公开交互思路，同时检查许可证和执行边界。将文件解析、凭据、网络与软件启动集中在 Rust 层，前端只通过类型化接口请求能力，减少界面组件直接访问系统资源的机会。

验收必须包含真实窗口和导出文件。仅检查 DOCX 是 ZIP、PDF 有页数或按钮存在，不能证明排版、图片和操作链路可用。清理中间文件以后必须再构建一次，避免实现隐含依赖开发输出目录。

## 2 信息安全

普通版不预置人员、工程、邮箱、模型密钥或开发电脑路径。Demo 数据明确标注合成，不使用真实芯片资料。原始案例模板中的人员水印、组织示例和内部填报链接不进入公开成果。

客户端默认拒绝网络访问；仅在用户开启连接、配置内网端点并主动执行操作时发送内容。模型密钥和邮箱密码交给系统凭据库；备份不包含凭据，恢复后回到离线状态。AI 请求关闭远端存储选项，但服务端实际保留政策仍需公司独立核实。

项目文件以只读方式授权。Markdown 不执行原始 HTML，远程图片被阻止；Skills 默认只允许说明与提示词类内容，不运行上传脚本。软件启动器不接受任意 Shell、参数或 URL。

正式交付需要分别检查源码、应用资源和二进制的敏感信息；依赖安全扫描不能保证不存在未知漏洞。公开版本不得附带真实内网验收记录。macOS 本地签名校验与公司 Developer ID 签名、公证是不同事项。

## 3 可推广性

适合单机资料整理、个人研发知识库以及允许本地或内网 AI 的研发支持场景。推广时先运行独立 Demo，再使用脱敏资料试用，最后由公司管理员验收模型、邮箱、证书、权限和备份流程。

不直接适用于多人实时协作、跨设备自动同步、强监管归档、大规模企业检索或自动 EDA 决策。此类场景应单独确认需求和安全方案，不能依靠修改界面文字宣称支持。

## 4 参考案例与开源项目

PDF.js（https://github.com/mozilla/pdf.js）用于离线 PDF 阅读；docx（https://github.com/dolanmiu/docx）用于结构化 Word 导出。两项实际依赖版本由锁文件记录。

Plane（https://github.com/makeplane/plane）、Joplin（https://github.com/laurent22/joplin）、FullCalendar（https://github.com/fullcalendar/fullcalendar）及 Qalculate（https://github.com/Qalculate/libqalculate）提供项目历史、笔记布局、日历与计算器的公开产品参考。仅参考不兼容许可证项目的交互思路，不复制其代码。完整来源、许可证和安全记录见 REFERENCES.md。

## 5 落地计划

软件首个正式版本与企业使用成熟度分别管理。依据模板中的五级文字定义，目前具有 M2 方案搭建与 Demo 证据；尚无足够证据认定完成 M3 真实业务试用，更不把发布版本号等同于 M4 生产就绪。

| 成熟度 | 日期或启动条件 | 计划与验收依据 |
| --- | --- | --- |
| M1 概念验证 | 2026-09-05 | 明确本地内网定位、需求范围和开源参考 |
| M2 方案搭建 | 2026-09-06 | 客户端、独立 Demo、自动回归和首版交付基线 |
| M3 早期试用 | 内网测试资源就绪后 | 业务人员使用脱敏任务；记录缺陷、耗时和导出质量 |
| M4 生产就绪 | 试用验收及组织批准后 | 完成目标平台、签名、公证策略、服务联调和支持流程 |
| M5 全面应用 | 稳定使用数据具备后 | 根据活跃使用、失败率和可复核收益决定推广范围 |

下一轮优先处理真实内网模型与邮箱兼容性、目标平台发布矩阵、复杂图文导入导出保真，以及笔记长时间编辑和恢复场景。新增跨设备、协同或 EDA 能力应重新立项确认。
