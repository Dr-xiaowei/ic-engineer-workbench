## 问题与经验

| 发现的问题 | 本次处理 | 后续保留的规则 |
| --- | --- | --- |
| PDF 能解析但桌面阅读空白 | 本地 PDF.js、worker、字体/CMap；静态绘制不依赖后台 RAF | 必须检查目标 WebView 中实际可见内容 |
| DOCX 只是装入 Markdown 字符串 | 改为标题、强调、列表、表格、图片的结构化导出，实际导出后渲染 | 检查内容与版式，不能只看扩展名和 ZIP 结构 |
| PDF 图片变成 base64 源码 | 增加内嵌图片和可搜索正文测试、视觉检查 | 为导出保留代表性图文样例 |
| 清理后编译引用失效 | Demo 改为引用版本控制中的集中合成资料 | 清理后重建，禁止依赖临时输出路径 |
| 切换笔记丢失编辑，映射只覆盖后续保存 | 笔记切换保护和既有笔记初始化映射 | 保存、切换、删除、目录不可用分别测试 |
| 源码无隐私但二进制有路径 | 编译路径重映射与最终包扫描 | 源码检查不能替代交付物检查 |
| 模拟测试被误当作工程验收 | 明确合成数据、协议测试和公司服务联调边界 | 不虚构 EDA 验证、生产联调或效率收益 |
| 浏览器登录不等于发布通道已就绪 | 官方 CLI 设备授权并核对系统网络通道 | 提前检查身份、仓库归属和上传能力 |

## 下一版建议

1. 优先完成公司模型与 IMAP/SMTP 的证书、认证、流式协议、文件夹和已发送行为验收，使用专用测试账户。
2. 确定目标系统/架构和组织签名、公证、升级回退策略；Linux GTK3 维护与健全性提示需独立复核。
3. 扩展复杂图文、合并表格、长表分页、损坏文档和大尺寸图片回归；不要把简单排版宣传为完整 Office 保真。
4. 增加跨模块草稿、异常退出恢复、映射目录离线、并发写入及磁盘满测试；统一事务和错误处理基础设施。
5. 通过相同脱敏任务测量查找耗时、摘要修正次数和失败率，具备可比较样本后才报告业务收益。

以上是后续建议，不自动视为已确认的新开发范围。多人协同、云同步、自动 EDA 等扩展必须重新确认需求。

## 下一次版本更新流程

读取 README、PROJECT、TASKS → 调研并确认需求 → 实现和回归 → 实际桌面与导出复核 → 依赖/许可证/安全审计 → 干净源码构建 → 普通版初态与 Demo 检查 → 签名和校验和 → 上传后重新下载核验。

每版只保留最终交付与必要源码资料。缓存、临时截图、测试导出和参考下载副本可重建；用户工程原件、运行数据和备份不能按开发垃圾删除。
